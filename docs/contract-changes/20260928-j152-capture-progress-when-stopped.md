## 变更内容

**一句话**:`scvb.captureProgress` 的周期帧仍只在播放中发;另加两个**例外帧** —— `mBridgeReady` 后首帧、
`clearCoverage` 受理后,各补发一次 **15 轨全量**,不看走带。

**为什么**:重开一个「采过、还没分析」的工程,停着打开 Output,Tab1 一直显示「当前范围内无采集数据」。
覆盖率只在播放中推,段表又是空的,分析行「覆盖 ∪ 段表」的判空两边都空。停着清除覆盖(§1.24),
契约许诺的「回推覆盖率变化」也要等下一次播放才兑现,数字不动。

### 分母为什么停着要取 max(播放头, 已采集末端)

例外帧多半发生在播放头停在 0 的时候(重开工程、宿主「播完回开头」)。沿用周期帧的 [0, 播放头),窗口就是空的,
已采集的覆盖一格都报不出来,等于没修。已采集末端与 §1.6 follow 档「分析全部」的终点是同一个量(v5.1 P1-F
同款理由);与播放头取大,是为了播放头停在已采集末端之后时,窗口仍盖得住走到过的地方。
这条口径随本卡派工一并给定,本 PR 按它实现。

**两个由此而来的现象(有意,不是缺陷)**:

- **清尾部时数字不一定下降**:已采集末端会跟着清除缩短,分母随之缩短。只剩一段 `[0,10)`、停在 0、清掉 `[5,10)`,
  清完仍报 100% —— 分母此时就是 §1.6 follow 档「分析全部」会作用的范围 `[0,5)`,这个数答的是「分析会作用的那段里
  有多少已采」,在这个意义上是真话。`HOST J152` ⑥b 把这一口径钉住。
- **从停着到开播,数字会跳一次**:例外帧(停着)的分母是 `[0, max(播放头, 已采集末端))`,周期帧(播放中)沿用既有的
  `[0, 播放头)`。从 0 开播时,前几帧的分母很短,数字会先跳到接近 100%(或 0%),再随播放头推进回到稳定值。
  两套口径叠出来的现象,不影响任何判定(分析按钮只看「有没有」,不看具体百分比)。

### 分母窗口为空时为什么照发

follow 态、从未采集、播放头在 0 时窗口为空。周期帧在这时不发(既有口径不动);例外帧**照发**,15 轨各报
`coveragePct:0`、`addedRanges:[]`。否则「停着把覆盖全部清掉」那一下,已采集末端归 0、窗口变空,界面上的数字
永远等不到归零 —— 正是例外② 要修的那一格。

## 兼容性影响

- **既有工程 / DAW 自动化**:零影响(不碰 state、参数、IPC)。
- **新旧版本互通**:桥面两端(C++ 与内嵌网页)随同一个插件包发布,不存在跨版本对端。
- **UI 侧随改一处**(不是契约面,记在这里是因为它是这次变更的直接后果):Tab1「范围内 {p}% 已覆盖」原先取
  「已报到的轨」的均值。例外帧 15 轨全带、没采过的轨报 0,照旧口径只用 4 轨的工程会显示 27%。
  改为取**采过的轨**的均值:此刻 > 0,或本会话里报过 > 0(`store.coverageSeen`)—— 后一半保证「整轨清光」的那条
  仍在分母里,清光 1 轨数字会降;已报到的轨全是 0 且都没采过时回 0(`web/output/tab-master.js` `coveragePercent`)。
  ⚠ `coverageSeen` 是**会话级**记账,随插件窗口重建而清空:关窗再开之后,之前被整轨清光的那条轨报 0、
  又不在记账里,会退出分母,数字按「此刻有覆盖的轨」算(4 轨清光 1 轨,同一次开窗内显示 75%,重开窗后显示 100%)。
  native 侧没有「这条轨采过」的持久记录可读;要做到跨会话一致,得换判据(例如按已连接的 Input 集合),留作后续。
- **只读观察实例**(O3)同样会在首帧收到一次全量:它不拉 feat 段,报的是它自己 FrameStore 里的覆盖。
  `clearCoverage` 对它本来就回 `{observer:true}`,不触发例外②。

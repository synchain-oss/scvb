## 变更内容

**一句话**:`lead_select` 选中的轨,由「只在播放时被强制拉到正中」改为**在分析里就被当作主唱**:该轨在它被选中的那些区间
并入集合 C(与 `lead_lock` 同一条路径 —— 恒居中、不占槽),其余声部按剩下的轨数排槽,音量平衡也把它当作居中的那一轨来算。
写进段表 / 打印进宿主自动化的曲线因此本身就体现了「主唱在中间、其余围绕它」。

**为什么要一份时间线记录**:`lead_select` 是宿主可自动化的参数(J58「每句换主唱」),插件拿不到宿主的自动化曲线,
只能在**播放经过时**看到它当下的值。所以:

1. Output 在走带播放(时间线有效、t0 ≥ 0)时,每个音频块把 `lead_select` 的值连同这一块的样本区间 push 进一个
   无锁单生产者单消费者队列(音频线程不分配、不加锁);
2. 消息线程每拍(以及点分析、存盘前)把队列排干进 `LeadTimeline`:样本域的分段常值记录,**后放覆盖先放**、相邻同值合并
   ([J143b] 每块还带写入来源,相邻两段值与来源都相同才合并);
3. 点分析时,计算窗内的记录随作业配置进管线;管线逐个全局区间取**多数值**(按已记录样本数,平局取小值);
   结果 n ∈ 1..15 且轨 n 在该区间活跃 ⇒ 该轨在这个区间按主唱锁处理。[J143b] **只取宿主写进来的记录**(自动化回放 /
   宿主参数面;插件界面、撤销 / 重做、载入工程写的值记下的段不看),它们盖不到的区间取点分析那一刻的 `lead_select`;
   一段宿主记录都没有时整窗都取后者。
4. 记录随工程落盘(`LEAD` 块),重开工程再分析,主唱仍在分析里。

**播放期覆盖层保留**(`DspArbiter` 的「选中轨 pan 目标 := 0」一句不动):按同一份记录分析过的区间里,主唱那一轨在它自己的段上
曲线本来就是 0,这一句不改变听到的东西;它仍兜住分析够不着的几种状态 —— 改了 `lead_select` 之后还没重新分析的区间、
冻结 pan 的轨(那一维读参数面,不读曲线)、跟随宿主档(不读曲线)、没有记录的旧工程。这些状态下「选中即居中」照旧成立,
但其余声部要等重新分析才会重新排布。

**`LEAD` 载荷**(小端):`u16 minor`(=2,[J143b];SL-216 首版为 1)| `u16` 保留(写 0)| `u32 条数`(≤ 65536)|
条数 × `{ i64 t0 | i64 t1 | u32 lead | u32 flags }`(每条 24 字节;t0 ≥ 0、t0 < t1、按 t0 升序互不重叠、lead ∈ 0..15、
`flags` bit0 = 宿主写的、其余位为 0)。minor 1 的记录是 `{ i64 t0 | i64 t1 | u32 lead }`(20 字节),照读、一律读成「不是宿主写的」。

| 读到的形态 | 处置 |
| --- | --- |
| 完整工程(带 `CFGS`)、有合法 `LEAD` | 记录整份换成它 |
| 完整工程、无 `LEAD`(旧工程 / 从没播过) | 记录清空 ⇒ [J143b] 重新分析时整窗按点分析那一刻的 `lead_select`;它为 0 时与改动前逐位相同 |
| 完整工程、`LEAD` minor 1(SL-216 首版格式) | 照读,每段读成「不是宿主写的」⇒ [J143b] 不算自动化 |
| 完整工程、`LEAD` 长度 / 顺序 / 值域 / `flags` 不合法 | 整块不用、记录清空(派生数据,重放一遍即可补回;不为它整份拒载工程) |
| 完整工程、`LEAD` 的 minor 高于本构建 | 按「没有记录」起步;保存时**原样回写**那份字节(自留一份,不依赖 `loadedChunks_`)。⚠ 这一状态下本构建新播的记录照样进分析,但**只在本次会话内有效** —— 存盘写回的是旧字节,重开后这些记录不在了 |
| 只带 `PRMS` 的轨道 / 参数预设 | 不动内存里的记录(与 FEAT / 通道配置同一个落点) |

## 设计取舍(交统筹核)

- **两条主唱**:`lead_select` 只能选一条;它与 `lead_lock` 的轨取并集进 C。C 本来就允许多轨共占中心(02 §5.2),
  不新增规则。⚠ Tracks 页「多主唱居中」琥珀提示只数 `lead_lock` 的轨(`web/output/tab-tracks.js`),
  `lead_select` 再选一条不同的轨时不会亮 —— 本卡不改 UI,记为待议项。
- **主唱是配对(pair)成员**:沿用 02 §5 既有优先级「lead_lock 优先,pair 忽略」—— 另一名成员按普通自由轨排。
- **主唱冻结了 pan / 不参与自动声像**:沿用既有分类优先级 leadLock > 冻结 pan > 不参与,分析里它都是 0;
  冻结轨播放时读参数面,由保留的覆盖层保证居中。
- **一个区间里主唱中途换人**:取多数值,不在换人处另切区间。全局区间由各轨段边界切出,通常比一句话短,换人又多落在句间,
  实际偏差是「晚一个区间换」。要按换人点精确切区间,得改 §3.4 的区间构造,不在本卡。
- **改了 `lead_select` 不自动重分析**:要点重新分析,与中心槽策略 / 响度口径「改后需重分析」同一类。[J143b] 在插件里改
  Lead Select 不必先播一遍,改完试听一段也不影响(插件写的值记下的段不看,没有宿主记录的地方按点分析那一刻的值);
  写了或改了宿主自动化才要把自动化所在的段落播一遍,让 Output 记下宿主写进来的值。
  自动重分析会在「每句换主唱」的自动化下每句触发一次,且每次都是一条撤销步,不可取。

## 兼容性影响

- **既有工程**:没有 `LEAD` 块 ⇒ 没有记录;播放期覆盖层照旧、段表不动 ⇒ **重开即听到的与改动前相同**(不重新分析就什么都不变)。
  [J143b] 重新分析时整窗按点分析那一刻的 `lead_select`:为 0 ⇒ 与改动前逐位相同;选了轨 n ⇒ 得到「主唱进分析」的新排布,不必先播一遍。
- **既有 DAW 自动化**:不受影响(参数面零变更;`lead_select` 仍不打印、host 恒权威)。
- **新旧版本互通**:新版写 → 旧版读,`LEAD` 按「未知 fourcc 原样保留回写」保真(旧版分析不读它);旧版写 → 新版读,无此块即「没有记录」。
  [J143b] 只认 minor 1 的构建(#305 之后、本卡之前的开发构建)读到 minor 2 ⇒ 按「minor 高于本构建」原样回写。
- **撤销 / 版本 / 冻结语义**:不变。记录是分析的输入(与 FEAT 同类),不进撤销栈、不分版本;分析本身的撤销照旧。

## 追加:J143 / J143a / J143b —— 点分析那一刻的 Lead Select(SL-545)

**缺口**:上面那套只认播放时的记录。而**采集本身就是走带播放** —— 采集过的地方全有记录,值是采集那会儿的
`lead_select`(通常 0)。于是「采完改了 Lead Select、不重播直接点分析」仍按记录里的 0 分析,选中的轨不居中;
旧工程(有特征、没有 `LEAD`)同理。

**J143**(统筹,2026-09-28):没有记录的区间用点分析那一刻的 `lead_select`,有记录的区间仍按记录。

**J143a**(统筹,同日;**已被 J143b 取代**):数计算窗里记录的不同值个数 —— ≤ 1 个 ⇒ 不算自动化、整窗用当前值;
≥ 2 个 ⇒ 按记录。它的坑(#317 复审【重要】1):采集把整条时间线记成 0,用户在插件里把 Lead Select 改成 3,
**试听了一小段**(那段记成 3)再点分析 ⇒ 窗里有 {0, 3} 两个值 ⇒ 被当成自动化 ⇒ 只有试听那段居中,其余照记录的 0。
用户没写任何自动化,旋钮全程就是一个值。

**J143b**(统筹,同日,取代 J143a):自动化证据按**写入来源**判,不按不同值个数判。一段记录只有当产生它的那次
改值**不是**插件自己写的(来自宿主自动化 / 宿主参数写入)才算自动化证据;用户在插件界面上的改动(桥面 → APVTS)
永远不算,撤销 / 重做写回的值、载入工程恢复的值同样不算。

| 计算窗里的记录 | 每个区间的主唱 |
| --- | --- |
| 没有宿主写的记录(没有记录 / 全是插件写的) | **整窗**取点分析那一刻的 `lead_select`(记录不看) |
| 有宿主写的记录 | 按**宿主记录**取多数值(平局取小值);宿主记录一个样本都盖不到的区间取点分析那一刻的值 |

**来源在哪里判**(实现):

- `analysis::LeadWriteOrigin`(core,JUCE-free):一个原子位「最近一次改值是不是宿主写的」+ 一个原子计数「插件写入进行中」。
- 插件自己写 `lead_select` 的三处都包 `LeadWriteOrigin::ScopedPluginWrite`(消息线程):`uiSetParam`(插件界面 ——
  桥面 `setParam` 的落点)、`paramWriter`(撤销 / 重做)、`setStateInformation` 里的 `replaceState`(载入工程 / 预设)。
  作用域一开就把来源**预置**成「插件」,再落值。
- 挂在 APVTS `lead_select` 上的参数监听器(构造期挂、析构摘)。JUCE 只在值**真的变了**时调它:宿主那一路是
  VST3 wrapper 的 `setValueAndNotifyIfChanged`(音频线程,同一次 process 里先于 `processBlock`),插件那一路在
  消息线程的作用域内。作用域外被调 ⇒ 宿主,作用域内 ⇒ 插件。
- `processBlock` 每块先读值(acquire)、后读来源,一起写进 `LeadRecorder`(无锁 SPSC、定长环、不分配);
  `LeadTimeline` 的每段带 `automated`,相邻两段只有值**与来源**都相同才合并。预置 + 先值后来源的次序保证
  音频线程最坏读到 (旧值, 插件),读不到 (新值, 宿主) —— 后者会凭空造出一截自动化证据。
- 管线:`majorityLead(automatedLeadRuns(leadRuns), 区间, leadFallback)`。区间都在计算窗里,窗里没有宿主记录
  ⇒ 每个区间都落到回落值 = 整窗用当前值;所以不另设「窗里有没有自动化」的分支(它与这一句结果恒同,删了也不会
  有用例变红)。`distinctLeadValues` 随 J143a 一起删除。

**`LEAD` 块 minor 1 → 2**:每条记录末尾加 `u32 flags`(bit0 = 宿主写的,其余位必须为 0,否则整块不用;记录
20 → 24 字节)。**容器 abi 不升**(仍为 6)。minor 1(SL-216 的格式,#305 引入、**从未随正式版发出**)照读,
**一律读成「不是宿主写的」**:那时不分来源,把它读成证据的话,开发期采集时记下的 0 会压住用户选的主唱 —— 正是
J143b 要修的坑;不读成证据,最坏只是那份开发期工程要把自动化段落重播一遍。只认 minor 1 的构建读到 minor 2
⇒ 走既有的「minor 高于本构建」一支:按没有记录分析、保存时原样回写。

**已知边角**(照实写,不是判据漏洞;USER_GUIDE 双语写明了前两条):

1. **自动化的值与此刻相同时看不见**:宿主写进来的值与此刻的值相同就不是一次改值,JUCE 不调监听器,来源保持
   上一次改值时的那个。典型:自动化开头那段的值恰好等于播放前的值(比如都是 0)⇒ 那一截记成插件写的、不算
   自动化,重新分析时按点分析那一刻的值 —— 播放头若停在自动化是别的值的地方,那一截就按停带位置的值排。
   补救:点分析前让 Lead Select 等于那一截应有的值(把播放头停在自动化是这个值的地方,或直接在插件里选它)。
2. **宿主参数面板 / 控制器改的也算自动化**:它们与自动化回放走同一条宿主写入路径,插件分不出来。
3. **计算窗是整条已采集时间线**(范围分析也一样):「有没有宿主记录」判的是全部已记录的部分,不只是这次选中的范围。
4. **插件写一次同值也把来源改成插件**(预置的副作用;监听器这次不会来):此后记下的段不算自动化,直到宿主下一次改值。
5. 插件写入的那几微秒里宿主恰好也在音频线程上改它 ⇒ 宿主那一笔记成插件写的(与 `AutomationPrinter` 自写位
   同一个窗口);宿主下一次改值即纠正。

**兼容性**:参数面、桥面零变化;`LEAD` minor 1 → 2,容器 abi 不变。已分析过的工程在重新分析之前段表不动(分析
只在点分析时跑);重新分析时按上表取值。冻结契约里受影响的句子一并订正:`docs/PARAMETERS.md` 的 `lead_select`
说明列;`docs/STATE_SCHEMA.md` §一 `lead_timeline[]`、§三 `LEAD` 的表行与说明(载荷、minor 1 的读法、「无此块」
那句兼容口径)。

## 变更内容

### 为什么是**新函数**而不是给 `setPanCurve` 加个开关

§1.17 的「撤销 = 是」「写 state」「经 `scvb.state` 回推」三行对预览**一条都不适用**。给旧函数加模式位
等于把这三行各劈成两半(SL-447 设计评估的结论,本 PR 照做)。新函数照 §1.5 `previewAnalyze` 的先例:
不写 state、不发事件、不落盘、不入撤销栈。

### §1.37 `previewPanCurve(v, points)` —— 要点

| 项 | 内容 |
| --- | --- |
| 做什么 | 把这份点表烘成 G 查表,**只换音频线程用的那一张**。已提交曲线仍只由 §1.17 改。 |
| 谁看得到预览 | 只有音频线程。存盘、`scvb.state` 回推、分析(左右平衡按 `pan_curve` 算)读的都是**已提交**点表;打印器与 viz **根本不读 G**(它们读各轨 pan/vol 曲线),预览对打印与 Monitor 零影响 —— 这就是裁定里「打印器只认松手后的曲线」在实现里的样子:不是加一道闸挡住打印器,而是打印器从来就不在 G 的读者名单里(`src/` 全仓核过:G 查表的读者只有 `DspArbiter` → `MixMath` 这条混音路径;分析那一侧的 `AutoAssign` 读的是已提交的**点表**,取自 `crvsData_`)。 |
| 撤销 | 否。撤销步仍由松手那一次 §1.17 产生:**一次手势一步**,与改前相同。 |
| 节奏(引擎侧,权威) | ① ≤20 Hz(两次生效间隔 ≥50 ms;烘表耗时会让消息线程占用超过 10% 时按实测耗时拉长);② 上一份预览被音频线程确认前不发下一份;③ 被拦下的不丢,只留最新一份、到点重试。UI 侧另节流 ≤20 Hz(不逐帧下发),节流窗里最后一份必发。 |
| `null` | 撤回预览,音频 30 ms 淡回已提交曲线。只读观察态下也受理(回到已提交曲线不是写入)。 |
| 自动作废 | §1.17 提交、该版本已提交曲线被改(撤销 / 重做 / 载入工程)、切版本、编辑器关闭。 |
| 松手 | §1.17 提交的点表与最后一份预览相同时,引擎**沿用预览那张表**:不重烘、LUT 指针不变 ⇒ 音频线程不开淡入窗口,松手那一下输出零变化。 |

### §1.17 改了什么、没改什么

「线程/频率」行原文「`pointerup`/工具条变更后提交,**节流 1 次/gesture,不逐帧下发**」**保留**,并补一段:
这一条对 `setPanCurve` 依然成立(一次手势 = 一次提交 = 一条撤销步);拖动期间的实时生效改走 §1.37;
提交时引擎顺带撤掉预览(沿用 / 重烘两种情形如上)。参数、返回、语义、拒绝态、撤销五行一字未动。

## 与 SL-445(#306 快照池回收)的关系 —— 用户问的「有没有冲突、会不会更严重」

**不冲突**:预览走的就是 #306 那条发布路径(`rebindSources` → `DspArbiter::publish` → 按
`oldestHeldSeq` 回收),没有另起第二套发布 / 保活机制,音频线程读快照的方式一行没改。

**不会更严重,而且在 #306 留下的那个缺口上更好**:#306 写明「只读观察 / 无时间线 / 无注入轨 / 宿主不调音频
时池只增不回收」。预览在这里多加了一道**回收闸**:上一份预览快照音频线程没越过,就不发下一份 ⇒ 任何时刻
至多一份预览未被确认。

| 场景 | 改前(只在松手时提交) | 本 PR(拖动实时预览) |
| --- | --- | --- |
| 音频在跑,连续拖 10 秒 | 拖动中 0 份,松手 1 份 | 200 份预览逐份发出,池峰值 **≤ 2**(音频线程手上那份 + 刚发的那份),旧预览表逐张释放、200 张里活着的 ≤ 2(`AUTH-PARAMS-18`) |
| 音频不在跑,连续拖 10 秒 | 拖动中 0 份,松手 1 份(不回收) | 只发出第 1 份,其余被回收闸拦下、只留最新一份待发 ⇒ **池只多 1 份**(`AUTH-PARAMS-17`);音频一跑起来下一拍就发最新那份 |
| 消息线程 CPU | 松手烘 1 张 | 每份一张;典型曲线 1–2 ms/张 × 20 Hz ≈ 2–5%;16 个 bell 约 16–19 ms/张,占空比上限把它压到约 5–6 Hz(≈10%)(`AUTH-PARAMS-19/20`,读数见 PR 描述) |

## 需要统筹过目的两处(实现方拍的细节,均在 J157 的实质之内)

1. **`v` 参数与 `staleVersion`**:预览带**点表捕获时**的版本号,引擎不等于当前版本就拒。
   理由:SL-451 已实测「切版本已发出、`scvb.state` 回声未到」窗口里任何 UI 侧版本判据都失灵;
   新函数没有历史包袱,一开始就带上版本号,预览就不会在那个窗口里串到新版本。代价是 §5.6 闭集 +1 值。
   **`setPanCurve` 本身不改**(SL-451 那一档仍在,不在 J157 范围内)。若统筹认为不该在本卡里加,
   去掉 `v` 只影响 §1.37 的参数行与 `staleVersion` 这一值,其余不变。
2. **占空比上限(10%)**:J157 要求「烘 128 KiB 表在 20 Hz 下若太重要换更便宜的预览路径」。实测典型曲线
   不重、极端曲线(16 个 bell)约占消息线程 1/3。没有换粗表(SL-447 评估已否:cut 在步长 2 就越 §7.2 的
   0.03 dB 线,且松手处会出台阶)、也没有另起烘表工作线程(多一条线程 + 交接 + 拆机顺序的新面),而是
   **按实测烘表耗时拉长间隔**:极端曲线预览更新变粗(约 5–6 Hz),消息线程占用封顶 10%。

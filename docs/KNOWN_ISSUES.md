## KI-1:run 切换时旧 run 尾部 ≤40ms 漏拉(04 异议 1)

- **现象**:增量拉取(04 §3.3)的读方以 base_hop 前后双读 + write_hop 做 seqlock 校验。若 run 切换(跳变 / 停止 / 开关)发生在两次 25Hz 轮询之间,旧 run 尚未拉取的尾部 hop 会被跳过,不并入 FrameStore。
- **原因**:FeatHeader 只有 base_hop / write_hop 两个寻址字段(ipc-contract §3 冻结布局),没有 run_id。切换后 base_hop 已指向新 run 起点,读方见 base != lastBase 即重置 lastPulled = base,旧 run 未拉积压整段跳过——旧 write_hop 已被新 run 覆盖,无法界定,永不补拉。
- **影响(已裁定接受)**:常态 ≤40ms(≈4 hop),且 run 切换通常落在换气/静音概率区,分析层 guard(04 §4.3 R⁺)与 padding 吸收;最坏情形 = 切换发生在 [M] 长停顿期间(加载工程/模态框/插件扫描,J10 场景),上限 = 停顿时长。**无假覆盖**:coverage 如实显洞 → UI 显示未采集 → 补播即复原。
- **缓解**:无(数据不可追回);后果可自愈(补播)。受限追赶(kMaxBurstHops=256)只保证 **run 不变**时的积压分拍补完,不覆盖 run 切换。
- **彻底修复方向**:FeatHeader 增 run_id(需 abi+1 且段名升 v2,04 文末异议 1 / J35)。v1 不做。

## KI-2:Cubase 15 下编辑器(WebView2)开不出来时的排查指引

- **现象**:暂无已确认故障。本条最初是**基线缺口登记**(当时 Cubase 15 上没有实测数据),不是已知 bug;现在保留为排查指引(见下「现状」)。
- **原因**:登记本条时,Cubase **15** 刚进入测试矩阵,其插件扫描/沙箱进程模型与 WebView2 子进程(`msedgewebview2.exe`)如何相处没有实测数据。已知风险面三处:
  1. **user-data 目录跨进程冲突**。宿主把插件扫描放在独立 sandbox 进程,音频进程与扫描进程同时活着;两进程若拿到同一个 user-data 目录,WebView2 环境创建会失败。**已修**:目录名带 PID(`PlatformWebView::makeUserDataFolder`),跨进程唯一。原实现只有进程内自增后缀,不同进程都拿 `_0`。
  2. **user-data 目录可写性**。目录已从 `%TEMP%` 迁到 `%LOCALAPPDATA%\Synchain\SCVB\WebView2`(`%TEMP%` 会被 Storage Sense 在会话中途扫掉),并在编辑器构造期建目录 + 写探针,结果进诊断面板。
  3. **子进程链被宿主策略挡掉**。插件侧无法规避,只能让它**可见**:导航事件一次都没来时,兜底面板直接显示「WebView2 环境没起来」而不是「加载太慢」。
- **影响**:无(三条都已转成可诊断状态)。
- **缓解**:测试包内附 `诊断.ps1`(= `scripts/check-webview2.ps1`),一次查完运行时版本 / user-data 可写性 / 子进程是否在跑。
- **现状**:此后 Cubase 15 Pro 上多轮成品测试包(2026-08 下旬 – 2026-09-28)的编辑器都能正常开窗使用,上述三处都没有再出现;本条保留,作为「编辑器开不出来」时的排查指引。
- **彻底修复方向**:**JUCE 侧有一处上游限制须记住**:`juce_WebBrowserComponent_windows.cpp` 把 `CreateCoreWebView2EnvironmentWithOptions` 与 `CreateCoreWebView2Controller` 两个完成回调的 HRESULT 形参都写成**无名参数直接丢弃**,失败时既不抛也不通知客户端。故「环境为什么没起来」的确切 HRESULT 在 JUCE 8.0.8 下拿不到,只能靠「导航事件从未到达」判定这一类。若后续需要精确 HRESULT,得自己直连 loader 复现一次环境创建(需引 `<WebView2.h>`),或向上游提 patch。

## KI-4:单轨渲染得到静音文件;替换式渲染会覆盖原素材(⚠ 用户数据)

- **现象**:对装了 SCVB Input 的**单条**人声轨做 Render in Place、Freeze 或单轨 stem 导出(这些渲染都会经过该轨的插件链),得到的是**静音**文件。如果宿主设置成用渲染结果**替换**原来的音频(替换式渲染),原素材就被这份静音结果替换掉了。
- **原因**:检测到健康的 SCVB Output 时,Input 会让本轨向下游输出静音(硬约束第 3 条),这条轨的声音改由 Output 在总线上求和后输出。单轨渲染只取这条轨自己的输出,所以是静音。
- **影响**:只渲染出一个静音文件时,重做即可;**替换式渲染会丢掉原素材**,是本条最要紧的后果。
- **缓解**:对**人声总线整体**导出(Cubase Export → Audio Mixdown、REAPER File → Render 等)。确实需要单轨素材时,先把这条轨上的 SCVB Input 旁路或移除再渲染,并且不要选「替换原音频」类选项;不确定时先备份工程和音频。
- **彻底修复方向**:无。这是「人声轨先、总线后」处理顺序(ADR-002)的直接后果,改掉静音通路就会破坏总线集中处理。

## KI-5:同一台机器同时开两个使用 SCVB 的工程,会互相抢 channel

- **现象**:同一台机器上同时开着两个使用 SCVB 的工程(两个 DAW,或同一个 DAW 的两个工程),而且两边用的是**同一个组**时,两边的 Input / Output 会落进同一个总线域:后开的一边可能报「channel 冲突」、第二个 Output 进入只读观察模式,不冲突的 Input 也可能连到另一个工程的 Output 上。
- **原因**:插件之间靠共享内存通信,共享内存段名只按组号(A–H)区分,不带工程标识(段名前缀 `SynchainSCVB.v1.` 是冻结契约,见 `docs/IPC_CONTRACT.md`)。
- **影响**:后开的工程得不到正确的平衡结果,两边的 channel 分配会互相干扰。
- **缓解**:同一时间只开一个使用 SCVB 的工程。确实需要同时开时,让两个工程用**不同的组**(八个组互相独立)。
- **彻底修复方向**:段名加入工程标识(documentToken)做隔离。改段名属于 IPC 布局改动,要升 abi 并把段名升 v2,v1 不做。

## KI-6:宿主停止调用 Output 后,人声约 5.5 秒无声,然后恢复成未平衡的原始声像

- **现象**:播放中宿主不经 bypass、直接停止调用 SCVB Output(Ableton Live 停用设备、FL Studio 的 smart disable 等;LUNA 的 Power 硬停用按设计预期同类,未实测)时,人声先**无声约 5.5 秒**,之后恢复成**未经平衡的原始声像**,并在整个停调期间保持这个原声。宿主重新调用 Output 后,三点要知道:
  - **长停调(已转成原声)逐轨接回**:已经转成原声的轨按通道号每隔约 0.2 秒接回一条平衡结果;第一条接回后 Output 就接管整条总线,**还没轮到的轨在轮到之前暂时无声**(排第 k 条的至少要等约 0.2 ×(k − 1)秒;停摆时有些轨已经静音、有些已转直通,直通轨还会白等前面轨占的位,所以这只是下限)。
  - **短停调当即接回**:停调不到约 5.5 秒、还没转成原声的轨,不排队,当即接回。
  - **恢复后最初约 80 毫秒**听到的是停调前混音的淡出,不是新的混音。
- **原因**:Output 被停调时自己不会收到任何通知。Output 一侧有一个看门狗:自己的处理计数停住 **≥0.5 秒**、同时仍有在线的人声轨在写数据,就判定「停摆」并断开连接,**整个停调期间保持断开**(闩住,不会自己又连回去);Input 随后按硬约束第 3 条的 **5 秒滞回**切回直通。0.5 + 5 ≈ 5.5 秒。停止播放时各轨都不写数据,看门狗不会误判。宿主恢复调用后,Output 按通道号错开约 0.2 秒放行各轨重新连接,这就是逐条接回的由来。
- **影响**:这 5.5 秒左右人声轨没有声音;之后听到的是未平衡的原始声像;恢复时按上面三点接回。(以前的版本判定停摆后只断开一瞬间就自己连了回去,人声会一直无声而不是 5.5 秒后转原声,已在 CHANGELOG #379 修复。)
- **缓解**:想做 A/B 对比时,不要停用设备,在 SCVB 面板里比:Output 的输出开关开 / 关,比的是「引擎曲线」与「宿主参数值」(没动过宿主参数时是默认值)这两种结果;Output 轨道页的「ON」开关是把这条轨从 SCVB 的输出里拿掉(见 KI-8),比的是「有这条轨」与「没有这条轨」。两者都不是「听未经处理的原声」;SCVB 没有听原声的即时开关。FL Studio 用户请对 SCVB Output 所在的总线关掉 smart disable(SCVB 的总线输入本来就是静音的,很容易被误挂起)。
- **彻底修复方向**:暂无计划。5 秒滞回是为了防止短暂卡顿时在「静音 / 直通」之间反复切换(J12 / J32),缩短它会把这类抖动带回来。

## KI-8:在 DAW 里静音、独奏人声轨或拉它的推子,SCVB 的输出不跟着变

- **现象**:对装了 SCVB Input 的人声轨按 DAW 的静音(Mute)或独奏(Solo),或者拉这条轨的推子,总线上听到的这条人声不变:静音了它照样响,独奏别的轨时它也还在,推子拉到底也照样有声。Cubase 上实测如此(S1 路由 spike 的 C-10,见 [DAW_COMPATIBILITY.md](DAW_COMPATIBILITY.md) §1 脚注 1);其他宿主没有逐一验证。
- **原因**:Input 插在人声轨插件链的最后一格、推子之前(硬约束第 2 条;Cubase 要放在 pre-fader 区),在那里把这条轨的声音交给总线上的 Output;这条轨自己向下游只输出静音(硬约束第 3 条)。DAW 的静音、独奏与推子作用在插件链之后,改变的只是那份静音,不是 Output 收到的声音。
- **影响**:习惯用 DAW 的静音 / 独奏做 A/B 或单听某个声部时,会以为操作没生效;用推子调的音量不会出现在 SCVB 的输出里。
- **缓解**:在 SCVB 里操作。要把某一轨从 SCVB 的输出里去掉,关掉 Output 轨道页该轨的「ON」开关(关着的轨也不会被写自动化);想单听某个声部,就把其余轨的「ON」关掉。要改某一轨的音量,用 SCVB 的手动微调或轨道页,不要拉 DAW 推子。
- **彻底修复方向**:无。这是「在插件链末格接走、由总线上的 Output 统一输出」这一架构(ADR-002 / J45)的直接后果。

## KI-9:齐唱 / 加倍(double)段落的平衡估算有偏差

- **现象**:几条轨唱同一句、声音高度相似的段落(齐唱、加倍轨),分析给出的音量与左右平衡听起来可能不如其他段落准:这些段落合起来往往比预想的更响,左右也可能略偏。
- **原因**:分析按「各轨声音互不相关」估算叠加后的响度与左右能量(平衡算法的能量相加模型)。互不相关的声音叠在一起,能量按相加算是准的;高度相关的声音会相干叠加,实际比估算更响 —— 两条完全相同的声音放在同一位置,实际比估算响约 3 dB,相同的轨越多差得越多。SCVB 不存音频(只存每 10 ms 一帧的特征),分析时没法按真实波形复核。
- **影响**:只影响这类段落的平衡结果,不影响其他段落,也不影响音频通路本身。
- **缓解**:听完觉得这些段落不平衡,用手动微调(见用户手册「手动微调」)修正这几段;手动改过的段不会被之后的自动重分析覆盖。
- **彻底修复方向**:要按真实波形复核就得存音频,v1 按设计不存(ADR-007),留待以后再议。

## KI-10:波形页上建选区、选段与改分段只能用鼠标

- **适用范围**:`v0.9.0-rc.N`。计划在 v1.0.0 之前补上键盘做法(J178)。
- **现象**:在 Output 的波形页(「波形与分段」)上,下面几件事只能用鼠标或触控板做,键盘做不了:在时间标尺上拖出选区;在泳道上点选一段;拖动段边界;在泳道上双击分割一段或删掉一条边界。这一页上的其他控件(工具条按钮、缩放条、泳道滚动区等)都能用 Tab 键到达;已经有选区时,选区两端的手柄也能用 Tab 键到达,并可用 ← / → 微调;选中相邻两段之后按 Delete 合并,按 Esc 取消选择。
- **原因**:段与段边界是画在画布上的,不是能获得键盘焦点的独立控件;时间标尺同样只响应鼠标。
- **影响**:只用键盘操作时,在波形页上建不了选区、选不了段,也就用不了要先有选区或选中段的功能 —— 局部重采集 / 重分析、段检查器里改 pan / vol(用户手册「局部重采集 / 重分析」「手动微调」)。其他三页不受这一条影响。
- **缓解**:这几步用鼠标或触控板做。
- **彻底修复方向**:v1.0.0 之前补上键盘建选区、选段与移动段边界的做法(J178)。

## KI-11:A 线(宿主调度加固)留下的几处残余

- **适用范围**:宿主调度加固一线(读方换代、正向在场与告警、挂起 ≠ 掉线,CHANGELOG #386 / #387 / #388)之后。编号 KI-11 由该线预分配,与其余条目一样不复用。
- **为什么五条放在同一个条目里**:它们是同一批修复留下的、都与「宿主谁先处理、谁提前处理」有关的边界,原因和缓解相近。逐宿主的说法留在 [DAW_COMPATIBILITY.md](DAW_COMPATIBILITY.md) 各宿主的「已知坑」里,只指回本条,不重复数字。
- **现象**(宿主触发条件一律是「可能」,不是每个宿主、每个工程都会出现):
  1. **句首可能少约 21 毫秒**:工程里有的轨被宿主提前处理(例如某条轨开着录音预备或输入监听,其余轨被 REAPER 的预先处理、Cubase 的 ASIO-Guard 一类机制提前算好)时,这样的轨从静音段(宿主暂停调用 Input、没有 region)恢复,句首可能少一小段 —— 最多一个写方块,约 21 毫秒。同步处理的轨在模拟宿主上句首不丢。
  2. **旁路超过约 5.5 秒再解除旁路**:旁路出来的原声直接停,SCVB 混音约 80 毫秒淡入(不再按交接握手平滑切回)。旁路短于 5.5 秒时本来就是这样。
  3. **人声总线上另有没装 Input 的声源**(和声轨、FX return、往总线送的 send),并且所有装了 Input 的轨在同一段间奏里一起被宿主挂起时:总线先回到原声,下一句开头约 80 毫秒淡入(与这次修复之前相同,不是回归)。总线上全是装了 Input 的轨时不会这样。
  4. **「路由失准」亮起的时间与宿主提前量有关**:人声轨没送进装 Output 的总线、或宿主先处理总线后处理人声轨时,提前量约 200 毫秒以内通常约 0.5 秒内亮;提前量越大亮得越晚,约为提前量的 2 倍。亮起之前这条轨照旧是静音的。
  5. **写方从一代开始就冻着的轨既不显示「挂起」也不报失准**(既有口径,没有变化):例如定位之后这条轨一直没被宿主调用过。它读不到数据、在混音里静音,但 Output 面板上既没有「暂无数据(挂起)」,也不会亮「路由失准」。
- **原因**:Output 读环时只能看到写方发布的两个数(代号与写头),看不出写方恢复时「从哪一帧开始写」,也分不清「还没轮到」与「一直读不到」;宽限和交叉都是为了不误报、不吃句首而取的保守值。设计口径见 [ARCHITECTURE.md](ARCHITECTURE.md) §5/§6,细节见变更文档 `contract-changes/20261009-a5-reader-generation-handover.md`、`20261011-a6-misalign-positive-presence.md`、`20261011-a8-suspend-not-offline.md`。
- **影响**:都只影响个别工程的个别时刻:第 1 条少听到约 21 毫秒句首;第 2、3 条多一次约 80 毫秒的淡入;第 4 条是告警晚亮;第 5 条是该轨无声而没有提示。
- **缓解**:第 4 条在告警亮起之前,发现某条人声轨无声时先查它是否送进了装 Output 的总线。第 5 条用 Output 轨道页核对每条轨的在线状态与数据。第 1、2、3 条没有用户侧开关,影响很小(Output 轨道页的「ON」开关是把这条轨从 SCVB 输出里拿掉,不能代替旁路去听原声)。
- **彻底修复方向**:第 1 条要读方知道写方的恢复点,需要改写方协议(布局 / abi),v1 不做;第 2、3 条要区分「旁路出来的原声」与「别的声源」,v1 不做;第 4 条在不增加误报的前提下缩短宽限,留待有更多宿主实测之后再议;第 5 条暂无计划。

## KI-12:macOS 上多个用户同时开 DAW,后开的连不上(EACCES)

- **适用范围**:macOS beta(Apple Silicon)。Windows 不受影响。编号 KI-12 起是 B 线(macOS)的条目,与其余条目一样不复用。
- **现象**:同一台 Mac 上有两个用户账号同时登录(快速用户切换)并都打开了使用 SCVB 的 DAW 时,后开的那一个里,Input 连不上 Output(共享内存打不开),Output 建不出自己的段。日志(`~/Library/Logs/Synchain/SCVB/`)里能看到 EACCES 一类的失败。
- **原因**:macOS 上的共享内存(POSIX shm)是整台机器共用的一个命名空间,段名是冻结契约(`docs/IPC_CONTRACT.md`),没有余量再带用户号;为了不让别的用户读写自己的段,段的权限是 0600,也不会去清别的用户名下的段。所以第二个用户拿不到第一个用户已经建好的同名段。
- **影响**:后开的那个用户的 SCVB 不工作(Input 保持直通,不会没有声音);先开的那个用户不受影响。
- **缓解**:同一时间只让一个用户账号开着使用 SCVB 的 DAW;先退出一个用户的 DAW 再在另一个用户里打开。这条与 KI-5(同一个用户开两个工程)是两件事,换组救不了它。
- **相关(未实测)**:插件若运行在 App Sandbox 里的宿主中,按设计预期也会因同一原因(沙盒对共享内存名和文件位置的限制)连不上;今天已知的目标宿主(LUNA、Logic 的 AUHostingService)没有这个限制,但沙盒宿主没有实测。
- **彻底修复方向**:段名加入用户号或工程标识,需要改冻结的段名(abi 与段名升 v2),v1 不做。

## KI-13:macOS 版没有签名也没有公证,必须自己执行 xattr

- **适用范围**:macOS beta。
- **现象**:从浏览器下载的 zip 解压出来的插件带着隔离属性(`com.apple.quarantine`)。不去掉它,宿主可能不列出 SCVB,或者在扫描时把它判为被拒绝(例如 LUNA 的 Plug-In Manager 显示 rejected);系统也可能弹出「无法验证开发者」之类的提示。
- **原因**:这个 beta 没有 Apple 开发者签名,也没有做公证,macOS 的 Gatekeeper 不放行带隔离属性的未签名代码。
- **影响**:装完不做处理就用不了;处理完之后行为与签名版没有区别。
- **缓解**:照 macOS zip 里 `INSTALL.txt` 的步骤,复制 bundle 之后执行 `xattr -dr com.apple.quarantine`(VST3 与 Component 两个目录各一条),再 `killall -9 AudioComponentRegistrar` 并让宿主重新扫描。用 `ditto` 复制,不要用 `cp -r`。
- **彻底修复方向**:正式版签名并公证。签名先不做,等评估;不在本条的承诺范围内。

## KI-14:macOS 版只有 arm64:不支持 Intel Mac,也不支持在 Rosetta 下运行的宿主

- **适用范围**:macOS beta。
- **现象**:Intel Mac 上装不了;Apple Silicon 上如果宿主本身通过 Rosetta 以 x86_64 运行,宿主不会列出 SCVB(或扫描失败)。
- **原因**:插件二进制只含 arm64 代码(打包脚本会断言这一点),没有 x86_64 切片;一个 x86_64 的进程不能加载 arm64 的插件。
- **影响**:这类机器 / 宿主用不了 macOS 版。
- **缓解**:用 Apple Silicon 的 Mac,并让宿主原生运行:在「访达」里选中宿主程序 > 文件 > 显示简介,取消勾选「使用 Rosetta 打开」(如果有这个选项)。宿主本身只有 Intel 版时没有办法。
- **彻底修复方向**:无计划。

## KI-15:不支持 GarageBand

- **适用范围**:macOS beta。
- **现象**:GarageBand 不会加载 SCVB,或者不会让它进入工程。
- **原因**:macOS 版的 `INSTALL.txt` 把 GarageBand 列为不支持。SCVB 要求宿主满足硬约束的摆法(Input 在人声轨最后一格、Output 在总线第一格),GarageBand 是否提供这样的插件槽位和总线,没有核实过,也没有在它里面测试过。
- **影响**:GarageBand 用户用不了。
- **缓解**:改用支持第三方 VST3 / Audio Unit 并有 Insert 与总线的宿主。Logic Pro 是 beta / 未在 Logic 实测,见 [DAW_COMPATIBILITY.md](DAW_COMPATIBILITY.md) §2.6。
- **彻底修复方向**:无计划。

## KI-16:系统 WebKit 低于 26.4 时,插件窗口的缩放固定在 100%

- **适用范围**:macOS beta。
- **现象**:在系统 Safari / WebKit 版本低于 26.4 的 Mac 上,插件窗口的缩放档位只剩 100%,其它档位被隐藏,界面上有一条说明。
- **原因**:插件界面用系统 WebKit(WKWebView)绘制。旧版 WebKit 在页面缩放后报告的鼠标坐标语义与新版不同,前端无法在所有缩放档位下把点击换算准确;为了不让点击和拖拽落点偏掉,旧语义下前端锁在 1.0。
- **影响**:界面不能放大(例如 125% / 150%);点击、拖拽的命中位置是准的。
- **缓解**:升级 macOS / Safari 到带 WebKit 26.4 或更高的版本。
- **彻底修复方向**:暂无计划;旧语义下的坐标换算是有意不做的取舍。

## KI-17:macOS 上编辑器有键盘焦点时,空格是否漏给宿主走带(未实测)

- **适用范围**:macOS beta。**本条是待核实项,不是已确认的故障。**
- **现象**:预期的行为是:插件编辑器窗口有键盘焦点时按空格,宿主走带不受影响或按宿主习惯响应。实际在 LUNA、Logic 里是否会让空格被编辑器吃掉或被宿主处理,没有在真机上看过。
- **原因**:插件界面是 WebView(WKWebView),键盘事件先交给网页;事件是否会再回到宿主,取决于宿主对插件窗口的处理,这一层无法在没有宿主的 CI 里验证。
- **影响**:最坏情形是编辑器有焦点时空格用不了宿主的走带快捷键。
- **缓解**:先把焦点点回宿主窗口再用空格;LUNA 验收会记录现象(`docs/validation/luna-acceptance.md` 的 UI 一项)。
- **彻底修复方向**:视验收结果决定;若确认漏键,再按宿主逐个处理键盘转发。

## KI-18:macOS 上开窗可能白闪;遮挡闸在 macOS 上关闭(未实测)

- **适用范围**:macOS beta。**本条是待核实项,不是已确认的故障。**
- **现象**:预期可能在插件窗口刚打开的第一帧前出现一闪而过的白色。是否真的出现、有多明显,没有在真机上看过。
- **原因**:Windows 上编辑器有一道「遮挡闸」,在首帧画好之前把窗口挪出屏幕外,避免白闪;这道闸只在 Windows 启用,macOS 上关闭(日志里的 `first-frame signal after … ms` 行会带 `(reveal gate off)`)。macOS 的 WKWebView 是否需要它,只能在真机上看。
- **影响**:最坏情形是开窗时有短暂的视觉闪烁,不影响音频和功能。
- **缓解**:无需处理;LUNA 验收会记录开窗是否白闪、日志里 reveal gate off 的行数。
- **彻底修复方向**:若验收看到白闪,再为 macOS 单独做一道首帧遮挡。

## KI-19:异常退出后遗留的共享内存段,要等下一个同名创建者或重启才清

- **适用范围**:macOS beta。
- **现象**:DAW 崩溃或被强杀之后,它建的共享内存段(名字形如 `SynchainSCVB.v1.…`)可能留在系统里,不会随进程消失。正常退出时,最后一个离开的插件会把段删掉,不会遗留。
- **原因**:POSIX 共享内存不随进程结束而释放,要等有人 `shm_unlink` 或重启。SCVB 用锁文件判断段有没有活着的持有者:DAW 崩溃时内核会放掉它持有的锁,所以下一个创建同名段的 SCVB 实例会发现没有持有者、把残段清掉再重建(只清自己用户名下的)。如果之后没有任何实例再建同名段,残段就一直留到重启。
- **影响**:残段不影响下一次使用(同名段会被重建);只是不会自己消失。它占多少内存没有专门核算。
- **缓解**:重启 Mac 会清掉所有残段;一般不需要处理。运行期间不要手动删除 `~/Library/Application Support/Synchain/SCVB/ipc` 这个锁文件夹,否则活着的实例和新实例会各用一份段。
- **彻底修复方向**:暂无计划;要主动回收需要一个独立的清理步骤,v1 不做。

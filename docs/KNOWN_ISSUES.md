## KI-1:run 切换时旧 run 尾部 ≤40ms 漏拉(04 异议 1)

- **现象**:增量拉取(04 §3.3)的读方以 base_hop 前后双读 + write_hop 做 seqlock 校验。若 run 切换(跳变 / 停止 / 开关)发生在两次 25Hz 轮询之间,旧 run 尚未拉取的尾部 hop 会被跳过,不并入 FrameStore。
- **原因**:FeatHeader 只有 base_hop / write_hop 两个寻址字段(ipc-contract §3 冻结布局),没有 run_id。切换后 base_hop 已指向新 run 起点,读方见 base != lastBase 即重置 lastPulled = base,旧 run 未拉积压整段跳过——旧 write_hop 已被新 run 覆盖,无法界定,永不补拉。
- **影响(已裁定接受)**:常态 ≤40ms(≈4 hop),且 run 切换通常落在换气/静音概率区,分析层 guard(04 §4.3 R⁺)与 padding 吸收;最坏情形 = 切换发生在 [M] 长停顿期间(加载工程/模态框/插件扫描,J10 场景),上限 = 停顿时长。**无假覆盖**:coverage 如实显洞 → UI 显示未采集 → 补播即复原。
- **缓解**:无(数据不可追回);后果可自愈(补播)。受限追赶(kMaxBurstHops=256)只保证 **run 不变**时的积压分拍补完,不覆盖 run 切换。
- **彻底修复方向**:FeatHeader 增 run_id(需 abi+1 且段名升 v2,04 文末异议 1 / J35)。v1 不做。

## KI-2:Cubase 15 下编辑器(WebView2)开不出来时的排查指引

- **现象**:暂无已确认故障。本条最初是**基线缺口登记**(当时 Cubase 15 上没有实测数据),不是已知 bug;现在保留为排查指引(见下「现状」)。
- **原因**:登记本条时,Cubase **15** 刚进入测试矩阵,其插件扫描/沙箱进程模型与 WebView2 子进程(`msedgewebview2.exe`)如何相处没有实测数据。已知风险面三处:
  1. **user-data 目录跨进程冲突**。宿主把插件扫描放在独立 sandbox 进程,音频进程与扫描进程同时活着;两进程若拿到同一个 user-data 目录,WebView2 环境创建会失败。**已修**:目录名带 PID(`PlatformWebView::makeUserDataFolder`),跨进程唯一。原实现只有进程内自增后缀,不同进程都拿 `_0`。
  2. **user-data 目录可写性**。目录已从 `%TEMP%` 迁到 `%LOCALAPPDATA%\Synchain\SCVB\WebView2`(`%TEMP%` 会被 Storage Sense 在会话中途扫掉),并在编辑器构造期建目录 + 写探针,结果进诊断面板。
  3. **子进程链被宿主策略挡掉**。插件侧无法规避,只能让它**可见**:导航事件一次都没来时,兜底面板直接显示「WebView2 环境没起来」而不是「加载太慢」。
- **影响**:无(三条都已转成可诊断状态)。
- **缓解**:测试包内附 `诊断.ps1`(= `scripts/check-webview2.ps1`),一次查完运行时版本 / user-data 可写性 / 子进程是否在跑。
- **现状**:此后 Cubase 15 Pro 上多轮成品测试包(2026-08 下旬 – 2026-09-28)的编辑器都能正常开窗使用,上述三处都没有再出现;本条保留,作为「编辑器开不出来」时的排查指引。
- **彻底修复方向**:**JUCE 侧有一处上游限制须记住**:`juce_WebBrowserComponent_windows.cpp` 把 `CreateCoreWebView2EnvironmentWithOptions` 与 `CreateCoreWebView2Controller` 两个完成回调的 HRESULT 形参都写成**无名参数直接丢弃**,失败时既不抛也不通知客户端。故「环境为什么没起来」的确切 HRESULT 在 JUCE 8.0.8 下拿不到,只能靠「导航事件从未到达」判定这一类。若后续需要精确 HRESULT,得自己直连 loader 复现一次环境创建(需引 `<WebView2.h>`),或向上游提 patch。

## KI-4:单轨渲染得到静音文件;替换式渲染会覆盖原素材(⚠ 用户数据)

- **现象**:对装了 SCVB Input 的**单条**人声轨做 Render in Place、Freeze 或单轨 stem 导出(这些渲染都会经过该轨的插件链),得到的是**静音**文件。如果宿主设置成用渲染结果**替换**原来的音频(替换式渲染),原素材就被这份静音结果替换掉了。
- **原因**:检测到健康的 SCVB Output 时,Input 会让本轨向下游输出静音(硬约束第 3 条),这条轨的声音改由 Output 在总线上求和后输出。单轨渲染只取这条轨自己的输出,所以是静音。
- **影响**:只渲染出一个静音文件时,重做即可;**替换式渲染会丢掉原素材**,是本条最要紧的后果。
- **缓解**:对**人声总线整体**导出(Cubase Export → Audio Mixdown、REAPER File → Render 等)。确实需要单轨素材时,先把这条轨上的 SCVB Input 旁路或移除再渲染,并且不要选「替换原音频」类选项;不确定时先备份工程和音频。
- **彻底修复方向**:无。这是「人声轨先、总线后」处理顺序(ADR-002)的直接后果,改掉静音通路就会破坏总线集中处理。

## KI-5:同一台机器同时开两个使用 SCVB 的工程,会互相抢 channel

- **现象**:同一台机器上同时开着两个使用 SCVB 的工程(两个 DAW,或同一个 DAW 的两个工程),而且两边用的是**同一个组**时,两边的 Input / Output 会落进同一个总线域:后开的一边可能报「channel 冲突」、第二个 Output 进入只读观察模式,不冲突的 Input 也可能连到另一个工程的 Output 上。
- **原因**:插件之间靠共享内存通信,共享内存段名只按组号(A–H)区分,不带工程标识(段名前缀 `SynchainSCVB.v1.` 是冻结契约,见 `docs/IPC_CONTRACT.md`)。
- **影响**:后开的工程得不到正确的平衡结果,两边的 channel 分配会互相干扰。
- **缓解**:同一时间只开一个使用 SCVB 的工程。确实需要同时开时,让两个工程用**不同的组**(八个组互相独立)。
- **彻底修复方向**:段名加入工程标识(documentToken)做隔离。改段名属于 IPC 布局改动,要升 abi 并把段名升 v2,v1 不做。

## KI-6:宿主停止调用 Output 后,人声约 5.5 秒无声,然后恢复成未平衡的原始声像

- **现象**:播放中宿主不经 bypass、直接停止调用 SCVB Output(Ableton Live 停用设备、FL Studio 的 smart disable 等;LUNA 的 Power 硬停用按设计预期同类,未实测)时,人声先**无声约 5.5 秒**,之后恢复成**未经平衡的原始声像**,并在整个停调期间保持这个原声。宿主重新调用 Output 后,三点要知道:
  - **长停调(已转成原声)逐轨接回**:已经转成原声的轨按通道号每隔约 0.2 秒接回一条平衡结果;第一条接回后 Output 就接管整条总线,**还没轮到的轨在轮到之前暂时无声**(排第 k 条的至少要等约 0.2 ×(k − 1)秒;停摆时有些轨已经静音、有些已转直通,直通轨还会白等前面轨占的位,所以这只是下限)。
  - **短停调当即接回**:停调不到约 5.5 秒、还没转成原声的轨,不排队,当即接回。
  - **恢复后最初约 80 毫秒**听到的是停调前混音的淡出,不是新的混音。
- **原因**:Output 被停调时自己不会收到任何通知。Output 一侧有一个看门狗:自己的处理计数停住 **≥0.5 秒**、同时仍有在线的人声轨在写数据,就判定「停摆」并断开连接,**整个停调期间保持断开**(闩住,不会自己又连回去);Input 随后按硬约束第 3 条的 **5 秒滞回**切回直通。0.5 + 5 ≈ 5.5 秒。停止播放时各轨都不写数据,看门狗不会误判。宿主恢复调用后,Output 按通道号错开约 0.2 秒放行各轨重新连接,这就是逐条接回的由来。
- **影响**:这 5.5 秒左右人声轨没有声音;之后听到的是未平衡的原始声像;恢复时按上面三点接回。(以前的版本判定停摆后只断开一瞬间就自己连了回去,人声会一直无声而不是 5.5 秒后转原声,已在 CHANGELOG #379 修复。)
- **缓解**:想做 A/B 对比时,不要停用设备,在 SCVB 面板里比:Output 的输出开关开 / 关,比的是「引擎曲线」与「宿主参数值」(没动过宿主参数时是默认值)这两种结果;Output 轨道页的「ON」开关是把这条轨从 SCVB 的输出里拿掉(见 KI-8),比的是「有这条轨」与「没有这条轨」。两者都不是「听未经处理的原声」;SCVB 没有听原声的即时开关。FL Studio 用户请对 SCVB Output 所在的总线关掉 smart disable(SCVB 的总线输入本来就是静音的,很容易被误挂起)。
- **彻底修复方向**:暂无计划。5 秒滞回是为了防止短暂卡顿时在「静音 / 直通」之间反复切换(J12 / J32),缩短它会把这类抖动带回来。

## KI-8:在 DAW 里静音、独奏人声轨或拉它的推子,SCVB 的输出大多不跟着变

- **现象**:Cubase 上,对装了 SCVB Input 的人声轨按 DAW 的静音(Mute)或独奏(Solo),或者拉这条轨的推子,总线上听到的这条人声不变:静音了它照样响,独奏别的轨时它也还在,推子拉到底也照样有声(S1 路由 spike 的 C-10,见 [DAW_COMPATIBILITY.md](DAW_COMPATIBILITY.md) §1 脚注 1)。REAPER 7.82 上推子同样不起作用,但静音和独奏不一样:静音会让这条轨从输出里消失;独奏实时不起作用,导出时却生效,文件里只剩独奏的那条。其他宿主没有逐一验证。
- **原因**:Input 插在人声轨插件链的最后一格、推子之前(硬约束第 2 条;Cubase 要放在 pre-fader 区),在那里把这条轨的声音交给总线上的 Output;这条轨自己向下游只输出静音(硬约束第 3 条)。DAW 的静音、独奏与推子作用在插件链之后,改变的只是那份静音,不是 Output 收到的声音。REAPER 上的静音和导出时的独奏让这条轨到不了 Output,具体机制没有细查。
- **影响**:习惯用 DAW 的静音 / 独奏做 A/B 或单听某个声部时,会以为操作没生效;用推子调的音量不会出现在 SCVB 的输出里。REAPER 上独奏实时听不出来,导出时却生效,文件里只剩独奏的那条,导出之前要看一眼有没有开着独奏。
- **缓解**:在 SCVB 里操作。要把某一轨从 SCVB 的输出里去掉,关掉 Output 轨道页该轨的「ON」开关(关着的轨也不会被写自动化);想单听某个声部,就把其余轨的「ON」关掉。要改某一轨的音量,用 SCVB 的手动微调或轨道页,不要拉 DAW 推子。
- **彻底修复方向**:无。这是「在插件链末格接走、由总线上的 Output 统一输出」这一架构(ADR-002 / J45)的直接后果。

## KI-9:齐唱 / 加倍(double)段落的平衡估算有偏差

- **现象**:几条轨唱同一句、声音高度相似的段落(齐唱、加倍轨),分析给出的音量与左右平衡听起来可能不如其他段落准:这些段落合起来往往比预想的更响,左右也可能略偏。
- **原因**:分析按「各轨声音互不相关」估算叠加后的响度与左右能量(平衡算法的能量相加模型)。互不相关的声音叠在一起,能量按相加算是准的;高度相关的声音会相干叠加,实际比估算更响 —— 两条完全相同的声音放在同一位置,实际比估算响约 3 dB,相同的轨越多差得越多。SCVB 不存音频(只存每 10 ms 一帧的特征),分析时没法按真实波形复核。
- **影响**:只影响这类段落的平衡结果,不影响其他段落,也不影响音频通路本身。
- **缓解**:听完觉得这些段落不平衡,用手动微调(见用户手册「手动微调」)修正这几段;手动改过的段不会被之后的自动重分析覆盖。
- **彻底修复方向**:要按真实波形复核就得存音频,v1 按设计不存(ADR-007),留待以后再议。

## KI-10:波形页上建选区、选段与改分段只能用鼠标

- **适用范围**:`v0.9.0-rc.N`。计划在 v1.0.0 之前补上键盘做法(J178)。
- **现象**:在 Output 的波形页(「波形与分段」)上,下面几件事只能用鼠标或触控板做,键盘做不了:在时间标尺上拖出选区;在泳道上点选一段;拖动段边界;在泳道上双击分割一段或删掉一条边界。这一页上的其他控件(工具条按钮、缩放条、泳道滚动区等)都能用 Tab 键到达;已经有选区时,选区两端的手柄也能用 Tab 键到达,并可用 ← / → 微调;选中相邻两段之后按 Delete 合并,按 Esc 取消选择。
- **原因**:段与段边界是画在画布上的,不是能获得键盘焦点的独立控件;时间标尺同样只响应鼠标。
- **影响**:只用键盘操作时,在波形页上建不了选区、选不了段,也就用不了要先有选区或选中段的功能 —— 局部重采集 / 重分析、段检查器里改 pan / vol(用户手册「局部重采集 / 重分析」「手动微调」)。其他三页不受这一条影响。
- **缓解**:这几步用鼠标或触控板做。
- **彻底修复方向**:v1.0.0 之前补上键盘建选区、选段与移动段边界的做法(J178)。

## KI-11:A 线(宿主调度加固)留下的几处残余

- **适用范围**:宿主调度加固一线(读方换代、正向在场与告警、挂起 ≠ 掉线、读方预拷贝,CHANGELOG #386 / #387 / #388 / #400)之后。编号 KI-11 由该线预分配,与其余条目一样不复用。
- **为什么七条放在同一个条目里**:它们是同一批修复留下的、都与「宿主谁先处理、谁提前处理」有关的边界,原因和缓解相近。逐宿主的说法留在 [DAW_COMPATIBILITY.md](DAW_COMPATIBILITY.md) 各宿主的「已知坑」里,只指回本条,不重复数字。
- **现象**(宿主触发条件一律是「可能」,不是每个宿主、每个工程都会出现):
  1. **句首可能少约 21 毫秒**:工程里有的轨被宿主提前处理(例如某条轨开着录音预备或输入监听,其余轨被 REAPER 的预先处理、Cubase 的 ASIO-Guard 一类机制提前算好)时,这样的轨从静音段(宿主暂停调用 Input、没有 region)恢复,句首可能少一小段 —— 最多一个写方块,约 21 毫秒。同步处理的轨在模拟宿主上句首不丢。宿主播放中重算提前处理的轨时(例如在还没播到的 region 上编辑,宿主把这条轨已经算好的部分作废、从当前播放位置重新算),同样可能少约 21 毫秒,位置在重算处、连续的音频中间。
  2. **旁路超过约 5.5 秒再解除旁路**:旁路出来的原声直接停,SCVB 混音约 80 毫秒淡入(不再按交接握手平滑切回)。旁路短于 5.5 秒时本来就是这样。
  3. **人声总线上另有没装 Input 的声源**(和声轨、FX return、往总线送的 send),并且所有装了 Input 的轨在同一段间奏里一起被宿主挂起时:总线先回到原声,下一句开头约 80 毫秒淡入(与这次修复之前相同,不是回归)。总线上全是装了 Input 的轨时不会这样。
  4. **「路由失准」亮起的时间与宿主提前量有关**:人声轨没送进装 Output 的总线、或宿主先处理总线后处理人声轨时,提前量约 200 毫秒以内通常约 0.5 秒内亮;提前量越大亮得越晚,约为提前量的 2 倍。亮起之前这条轨照旧是静音的。
  5. **写方从一代开始就冻着的轨既不显示「挂起」也不报失准**(既有口径,没有变化):例如定位之后这条轨一直没被宿主调用过。它读不到数据、在混音里静音,但 Output 面板上既没有「暂无数据(挂起)」,也不会亮「路由失准」。
  6. **被提前处理的轨循环时,每圈回到起点之前可能少一小段**:在模拟宿主上最多一个写方块(约 21 毫秒),与圈长无关 —— 读方最后一次看到上一圈之后、写方又写的那一截来不及确认。读方预拷贝(CHANGELOG「修复」里圈长接近约 10.9 秒整数倍的那一条)之前,圈长落在约 10.9 秒(48 kHz)整数倍前后一个提前量之内时每圈少约一个提前量;现在这一带也只少这一截。少数情形下这一圈仍可能像以前一样少约一个提前量:宿主在回绕前一刻才一口气补渲染了一大段;提前量超过约 2.7 秒(48 kHz,读方的拷贝装不下);Input 与 Output 真正并发处理的宿主上,回绕恰好撞上写方换代、还没写出第一段的那一瞬间。
  7. **循环播放中途改了内容、宿主又在新一圈里暂时不调用 Input 时,可能听到上一圈的旧音频**(既有口径,v0.9.0-rc.1 也一样,不是这批修复引入的):例如播放中删掉或改短了还没播到的 region,宿主在那一段不再调用这条轨的 Input。Output 走到写方停住的位置之后,读到的是上一圈在同一位置留下的音频 —— 位置是对的,内容是改之前的。在模拟宿主上,提前量较小(约 85 毫秒)、2 秒的循环、写方在新一圈停 1 秒时,最多约 0.9 秒;提前量 1 秒时没有出现。宿主照常调用 Input(只是输出静音)时不会这样。
- **原因**:Output 读环时只能看到写方发布的两个数(代号与写头),看不出写方恢复时「从哪一帧开始写」,也分不清「还没轮到」与「一直读不到」;宽限和交叉都是为了不误报、不吃句首而取的保守值。第 6 条是读方给自己留的拷贝覆盖不到的那一截:拷贝只装得下读方确认过的数据,确认之后写方又写的那一段证明不了来历。设计口径见 [ARCHITECTURE.md](ARCHITECTURE.md) §5/§6,细节见变更文档 `contract-changes/20261009-a5-reader-generation-handover.md`、`20261011-a6-misalign-positive-presence.md`、`20261011-a8-suspend-not-offline.md`、`20261014-a16-reader-precopy.md`。
- **影响**:都只影响个别工程的个别时刻:第 1 条少听到约 21 毫秒(句首或重算处);第 2、3 条多一次约 80 毫秒的淡入;第 4 条是告警晚亮;第 5 条是该轨无声而没有提示;第 6 条是循环每圈结尾少听到约 21 毫秒(少数情形下约一个提前量),不错音、不报警;第 7 条是改动之后可能多听到不到一秒改之前的内容。
- **缓解**:第 4 条在告警亮起之前,发现某条人声轨无声时先查它是否送进了装 Output 的总线。第 5 条用 Output 轨道页核对每条轨的在线状态与数据。第 1、2、3、6、7 条没有用户侧开关,影响很小(Output 轨道页的「ON」开关是把这条轨从 SCVB 输出里拿掉,不能代替旁路去听原声)。
- **彻底修复方向**:第 1 条要读方知道写方的恢复点(或重算起点),需要改写方协议(布局 / abi),v1 不做;第 6 条同理(要读方知道写方最后一笔写到哪才算数),v1 不做;第 2、3 条要区分「旁路出来的原声」与「别的声源」,v1 不做;第 4 条在不增加误报的前提下缩短宽限,留待有更多宿主实测之后再议;第 5 条暂无计划;第 7 条要读方在自己回绕之后不再认上一圈的数据,这会改变各类宿主在循环点上的现有行为,要先有更多宿主实测,beta 之后再议。

## KI-12:macOS 上多个用户同时开 DAW,后开的连不上(EACCES)

- **适用范围**:macOS beta(Apple Silicon)。Windows 不受影响。编号 KI-12 起是 B 线(macOS)的条目,与其余条目一样不复用。
- **现象**:同一台 Mac 上有两个用户账号同时登录(快速用户切换)并都打开了使用 SCVB 的 DAW 时,后开的那一个里,Input 连不上 Output(共享内存打不开),Output 建不出自己的段。日志(`~/Library/Logs/Synchain/SCVB/`)里能看到 EACCES 一类的失败。
- **原因**:macOS 上的共享内存(POSIX shm)是整台机器共用的一个命名空间,段名是冻结契约(`docs/IPC_CONTRACT.md`),没有余量再带用户号;为了不让别的用户读写自己的段,段的权限是 0600,也不会去清别的用户名下的段。所以第二个用户拿不到第一个用户已经建好的同名段。
- **影响**:后开的那个用户的 SCVB 不工作(Input 保持直通,不会没有声音);先开的那个用户不受影响。
- **缓解**:同一时间只让一个用户账号开着使用 SCVB 的 DAW;先退出一个用户的 DAW 再在另一个用户里打开。这条与 KI-5(同一个用户开两个工程)是两件事,换组救不了它。
- **相关(未实测)**:插件若运行在 App Sandbox 里的宿主中,按设计预期也会因同一原因(沙盒对共享内存名和文件位置的限制)连不上;今天已知的目标宿主(LUNA、Logic 的 AUHostingService)没有这个限制,但沙盒宿主没有实测。
- **彻底修复方向**:段名加入用户号或工程标识,需要改冻结的段名(abi 与段名升 v2),v1 不做。

## KI-13:macOS 版没有签名也没有公证,必须自己执行 xattr

- **适用范围**:macOS beta。
- **现象**:从浏览器下载的 zip 解压出来的插件带着隔离属性(`com.apple.quarantine`)。不去掉它,宿主可能不列出 SCVB,或者在扫描时把它判为被拒绝(例如 LUNA 的 Plug-In Manager 显示 rejected);系统也可能弹出「无法验证开发者」之类的提示。
- **原因**:这个 beta 没有 Apple 开发者签名,也没有做公证,macOS 的 Gatekeeper 不放行带隔离属性的未签名代码。
- **影响**:装完不做处理就用不了;处理完之后行为与签名版没有区别。
- **缓解**:照 macOS zip 里 `INSTALL.txt` 的步骤,复制 bundle 之后执行 `xattr -dr com.apple.quarantine`(VST3 与 Component 两个目录各一条),再 `killall -9 AudioComponentRegistrar` 并让宿主重新扫描。用 `ditto` 复制,不要用 `cp -r`。
- **彻底修复方向**:正式版签名并公证。签名先不做,等评估;不在本条的承诺范围内。

## KI-14:macOS 版只有 arm64:不支持 Intel Mac,也不支持在 Rosetta 下运行的宿主

- **适用范围**:macOS beta。
- **现象**:Intel Mac 上装不了;Apple Silicon 上如果宿主本身通过 Rosetta 以 x86_64 运行,宿主不会列出 SCVB(或扫描失败)。
- **原因**:插件二进制只含 arm64 代码(打包脚本会断言这一点),没有 x86_64 切片;一个 x86_64 的进程不能加载 arm64 的插件。
- **影响**:这类机器 / 宿主用不了 macOS 版。
- **缓解**:用 Apple Silicon 的 Mac,并让宿主原生运行:在「访达」里选中宿主程序 > 文件 > 显示简介,取消勾选「使用 Rosetta 打开」(如果有这个选项)。宿主本身只有 Intel 版时没有办法。
- **彻底修复方向**:无计划。

## KI-16:macOS 上插件窗口的缩放改走 WebKit 原生页面缩放(CI 探针已验,待 LUNA 真机确认)

- **适用范围**:macOS beta。
- **现象(改前)**:插件窗口的缩放档位只剩 100%,其它档位被隐藏,界面上有一条说明。在笔记本这类小屏幕上 Output 的窗口偏大,也改不小(用户在 macOS 15.6.1 + LUNA 上实测)。原先以为只有 Safari / WebKit 低于 26.4 的系统才会这样;CI 探针在 macOS 15.8.2 / Safari 27.2 的 WKWebView 里量到的仍是旧语义,所以「Safari 低于 26.4」这条分界不成立;嵌在宿主里的 WKWebView 实际用哪种语义,以探针实测为准。
- **原因**:插件界面用系统 WebKit(WKWebView)绘制,以前用 CSS zoom 缩放。旧语义下,CSS zoom 之后元素位置按未缩放的坐标报,鼠标坐标却是缩放后的,点击和拖拽会落偏;为了不落偏,前端在旧语义下锁在 100%。
- **现在的做法**:mac 上缩放改走 WKWebView 的原生页面缩放(`pageZoom`),页面里的 CSS zoom 恒为 1。元素位置和鼠标坐标落在同一个坐标系里,不分新旧语义都对得上,所以三个插件的档位全部开放;Output 在 mac 上新开时默认 80%(全局默认档位与工程里存的档位仍然优先)。档位高于 100% 时,Output 母带页 / 波形页的画布和 Monitor 的轨迹图按档位提高分辨率;Output 曲线编辑器和引导页的画布只按屏幕像素比,档位高于 100% 时略软(Windows 上一直如此)。
- **验证到哪一步**:CI 上的真 WebKit 探针(`tests/macos/pagezoom-probe`,在 macOS 15.8.2、Safari 27.2、旧语义、1x 屏幕上跑)跑的是产品自己的页面脚本,对七个档位逐档核对视口大小、元素位置、`elementFromPoint` 和真实鼠标点击,点击全部落在该落的元素上;实测 pageZoom 不改 `devicePixelRatio`,重新导航后 pageZoom 也还在。**还没在 LUNA 或其它真实宿主里确认**,也没有在 Retina 屏上量过,由 [LUNA 验收](validation/luna-acceptance.md) 的 UI 一项核对。
- **影响**:如果某个宿主里原生缩放没生效,页面会量到视口跟着窗口变了,自己退回改前的做法:WebKit 是旧语义时锁在 100%,只剩 100% 一档,窗口改回 100%,并显示那条说明,点击不会落偏;是新语义时照旧用 CSS zoom 按档位缩放。插件找不到 WKWebView 时,`~/Library/Logs/Synchain/SCVB/` 下对应插件的日志里还会有一行 `native page zoom: no WKWebView under the browser component, page falls back to CSS zoom`。mac CI 在带界面的 pluginval 开过 Output 之后检查它的日志:必须有 `native page zoom <档位>`,不能有这一行。
- **缓解**:遇到档位只剩 100%,或者点击落偏,把上面那个日志文件夹带回来;点击落偏时先把档位改回 100%。
- **彻底修复方向**:LUNA 真机确认之后,按结果关闭或改写本条。

## KI-17:macOS 上编辑器有键盘焦点时,空格是否漏给宿主走带(未实测)

- **适用范围**:macOS beta。**本条是待核实项,不是已确认的故障。**
- **现象**:预期的行为是:插件编辑器窗口有键盘焦点时按空格,宿主走带不受影响或按宿主习惯响应。实际在 LUNA、Logic 里是否会让空格被编辑器吃掉或被宿主处理,没有在真机上看过。

- **影响**:最坏情形是编辑器有焦点时空格用不了宿主的走带快捷键。
- **缓解**:先把焦点点回宿主窗口再用空格;LUNA 验收会记录现象(`docs/validation/luna-acceptance.md` 的 UI 一项)。

## KI-18:macOS 上开窗可能白闪;遮挡闸在 macOS 上关闭(未实测)

- **适用范围**:macOS beta。**本条是待核实项,不是已确认的故障。**
- **现象**:预期可能在插件窗口刚打开的第一帧前出现一闪而过的白色。是否真的出现、有多明显,没有在真机上看过。

## KI-19:异常退出后遗留的共享内存段,要等下一个同名创建者或重启才清

- **适用范围**:macOS beta。
- **现象**:DAW 崩溃或被强杀之后,它建的共享内存段(名字形如 `SynchainSCVB.v1.…`)可能留在系统里,不会随进程消失。正常退出时,最后一个离开的插件会把段删掉,不会遗留。
- **原因**:POSIX 共享内存不随进程结束而释放,要等有人 `shm_unlink` 或重启。SCVB 用锁文件判断段有没有活着的持有者:DAW 崩溃时内核会放掉它持有的锁,所以下一个创建同名段的 SCVB 实例会发现没有持有者、把残段清掉再重建(只清自己用户名下的)。如果之后没有任何实例再建同名段,残段就一直留到重启。
- **影响**:残段不影响下一次使用(同名段会被重建);只是不会自己消失。它占多少内存没有专门核算。
- **缓解**:重启 Mac 会清掉所有残段;一般不需要处理。运行期间不要手动删除 `~/Library/Application Support/Synchain/SCVB/ipc` 这个锁文件夹,否则活着的实例和新实例会各用一份段。
- **彻底修复方向**:暂无计划;要主动回收需要一个独立的清理步骤,v1 不做。

## KI-20:单声道轨和宽立体声轨混用时,分析后左右可能偏 2–3 dB

- **现象**:同一组里既有单声道轨,又有左右内容不同的宽立体声轨时,分析后的混音可能偏向一侧,默认宽度下约 2–3 dB。调宽全局 Width 时偏得更多。同组立体声轨的 width 调得不一样时也可能出现。
- **原因**:算左右平衡时,分析把立体声轨当成它声像位置上的一个点,不读你调的 width。实际播放时,立体声轨的两个声道落在两个子声像上,左右差比一个点小得多。单声道轨确实是一个点,所以两种轨混用时,分析算出的左右差和实际对不上。
- **影响**:只影响这类组合的左右平衡,不影响音频通路本身。全是立体声轨、宽度相同、声像自动分配时不受这条影响:模拟里平均偏差 0.1–0.2 dB。单声道人声放在立体声轨上(左右内容相同)再和单声道轨混用时,平均偏差 0.4–0.6 dB。
- **缓解**:用手动微调(见用户手册「手动微调」)修正;手动改过的段不会被之后的自动重分析覆盖。
- **彻底修复方向**:把分析改成按两个子声像算,但不能只改这一处:模拟里只改这一处,全是立体声轨的工程偏差反而变大,回退和警告明显变多。要先重新评估平衡求解器。

## KI-21:实时播放时,开头可能先有一小段原声或短暂无声(约 0.1–0.3 秒)

- **现象**:下面几种情况按播放(或从 DAW 窗口实时渲染)时,开头约 0.1–0.3 秒听到的是未经平衡的原声,或者有一小段无声,之后才是平衡结果:
  - 走带停了超过约 5.5 秒再播(这时各轨已经回到原声);
  - 从 DAW 窗口实时渲染,或者宿主在按播放时重新准备插件(Input 回到原声);
  - 定位之后不到约 40 毫秒就按播放;
  - 按播放之前 DAW 的主线程卡住超过 2 秒(比如刚打开很大的工程)。

  停走带不到约 5.5 秒、从停住的位置直接播放时没有这一段:第一块就是平衡结果(80 毫秒淡入)。
- **原因**:这些情况下 Output 在第一块还确认不了每条 Input 都已经静音、而且就是从停住的位置开始写的,只能等主线程下一拍按原来的交接协议(J32)接手:先让 Input 静音,确认之后 Output 再接上。主线程按 25 Hz 跑,交接要一到几拍。主线程卡住之后补跑的那几拍还会看到 Input 的心跳过期,要再多等一会儿。
- **影响**:只影响开头这一小段,之后的混音不受影响。离线导出不走这条,不受影响。
- **缓解**:要听平衡后的开头,停走带不要超过约 5 秒,从停住的位置播;导出成品用离线渲染。
- **彻底修复方向**:暂无计划。起播时 Output 要先有证据确认 Input 是从这里起写的,否则会把环里的旧内容当成新数据读出来;Input 还在直通时提前接上会两路叠加(J32 禁止)。

## KI-22:实时交接时宿主主线程卡住,中间会有一段无声

- **现象**:KI-21 那几种情况下,开头是从原声交叉到混音。如果交接那一刻宿主的主线程卡住,Input 已经静音、Output 还没接上,这段总线上没有声音,长度等于卡住的时间。实测:REAPER 7.82 放在看不见的 Windows 桌面上(另一个桌面,没有窗口能在前台)从窗口实时渲染,开始渲染后主线程停了约 1.46 秒,导出文件 0.33 秒起约 1.3 秒全零,11 次都这样;同一个工程放在看得见的桌面上 28 次都没有,只在交接处有一个约 0.05 秒的短凹陷。
- **原因**:实时交接(J32)是 Input 先静音,Output 的 [M](主线程 25 Hz)看到 Input 已静音之后才接上。Input 的静音也由它自己的主线程定时器决定。Input 那一拍刚静音、Output 下一拍还没来时主线程卡住,中间就空了。停走带不到约 5.5 秒、从停住的位置播放时,Output 第一块就接上(KI-21),不受影响;离线导出不受影响。
- **影响**:只在交接那一下、主线程恰好卡住时出现,之后的混音正常。锁屏或远程桌面断开时实时渲染会不会这样,没有实测。
- **缓解**:实时渲染时让 REAPER 所在的桌面保持可见;导出成品用离线渲染。
- **彻底修复方向**:Output 的 [A] 在音频线程上自己看 Input 的 muted 位就开始读,不等 [M] 下一拍(起播第一块已经这样做)。要补冻结文档的措辞,计划下一版做。

## KI-23:接在 Input 之后的发送和 stem,开头有一小段原声,之后是静音

- **现象**:装了 SCVB Input 的轨,自己向下游的输出开头还有几块原声,之后才静音,组总线上的 Input 也一样。REAPER 7.82 离线导出实测是 1–3 块(一层工程单独测的,48 kHz:块大小 512 时 10.7–32 毫秒,64 时 3–4 毫秒,1024 时 21–43 毫秒),块数逐轨、逐次不同。所以这条轨的 stem、接在 Input 之后的发送,开头这几块有声,两次导出的这几块可能不同,之后全是静音。从 REAPER 窗口实时渲染时,组总线上的 send 开头约 0.4 秒都有声;这段 send 如果又回到主输出,会和正常输出叠在一起,测试信号的峰值高了约 10 dB。
- **原因**:连上健康的 Output 之后 Input 才静音(硬约束第 3 条)。Input 要在 Output 读到之后、自己处理的下一块才静音,宿主让写方提前跑时更晚(`docs/IPC_CONTRACT.md` §2)。之后的静音是设计如此:这条轨的声音已经交给 Output。
- **影响**:只影响单独取 Input 轨的 stem,和接在 Input 之后的发送。主输出不受影响:离线导出从第一个样本起就和不插插件的混音一致(差别在 -150 dB),两次导出逐位相同。
- **缓解**:导出主输出或总线,不要从 Input 之后取声音。要给一条轨或一组加效果,插在 Input 之前。
- **彻底修复方向**:无。Input 只有确认 Output 读到之后才能静音,否则会丢声音。

## KI-24:报告延迟的插件排在 Input 或上层 Output 之前时,导出开头不足一块是原声

- **现象**:工程里有报告延迟的插件,而且它排在某个 Input 之前(人声轨上,或组总线的 Output 和 Input 之间),或者排在上层 Output 之前时,离线导出的文件最开头不足一块和正常结果不同,听到的是原声。REAPER 7.82 上块大小 512 时约 9 毫秒,一层和两层工程都有。之后逐位相同。插件排在 Input 之后,或者排在下层 Output 之前、上层 Output 之后时,没有这一段。
- **原因**:和宿主的延迟补偿有关,具体时序没有细查。
- **影响**:只有文件最开头这一点,而且只在有这类插件时出现。工程开头是静音时听不出来。
- **缓解**:导出区间从内容开始之前起。
- **彻底修复方向**:暂无计划。

## KI-25:嵌套接错时大多不报错

- **现象**:嵌套(两层 SCVB)接错时,大多没有提示,或者提示指不到真正的原因。最容易误判的两种:组总线或上层总线上多插一个同组的 Input,导出和正确接法相同,实时却没声音;组总线没送进上层总线、直接送主输出,导出基本正常,实时这组没声音。逐项见[用户手册](USER_GUIDE.zh-CN.md)「嵌套:两层 SCVB」的「接错时的后果」。
- **原因**:每个 Input 和 Output 只看得到自己这一组,判断不出整条链接得对不对。这些接法在共享内存这一层都是合法的。
- **影响**:只影响嵌套用法。自环不会啸叫,也不会出现爆音或非法值。
- **缓解**:照手册的接法表接;某一组没声音时先对照上面那张表。
- **彻底修复方向**:暂无计划。

## KI-26:REAPER 上 Write 写出的车道,开头约 0.3 秒不准

- **现象**:REAPER 7.82 上按 Write 从头写一遍,车道要到约 0.29 秒才到曲线的值:这之前有一段回到写入前的值,落在 0.21–0.29 秒。走带停下之后,车道末尾还会多一小段回到写入前的值。在两层工程上测到,一层工程没有单独看。
- **原因**:没有细查。写入是主线程按 25 Hz 发出的,很可能和这个有关。
- **影响**:输出开关开着时 DSP 用引擎值,不读车道,听到和导出的都不受影响:写过车道和没写过的工程,导出逐位相同。输出关掉、靠车道回放时,开头这一小段的声像和音量不准。
- **缓解**:要靠车道回放时,从内容开始之前写起,或者手动修开头这几个点。
- **彻底修复方向**:暂无计划。

## KI-27:从 REAPER 窗口离线导出,偶发整个文件无声

- **现象**:REAPER 7.82 上打开一层工程、等 3 秒后从窗口离线导出(Full-speed Offline),68 次里有 1 次整个文件是静音(8 秒全零)。同一个工程其余 67 次都正常,和命令行导出的结果逐位相同。出现的那一次是一轮测试里的第一次窗口导出。之后加了诊断又试了 40 次,没有再出现。
- **原因**:没查清,也还不能确定是 SCVB 的问题还是测试环境的问题。SCVB 这边最可能的位置是离线交接:Output 对第一块的判定,和 Input 什么时候静音。
- **影响**:见到的那一次是整个文件无声,听一下或看一眼波形就能发现。
- **缓解**:导出之后看一眼波形;无声就再导出一次。
- **彻底修复方向**:下一版给离线交接加诊断(第一块的判定、Output 从哪里开始读),复现之后再定。
